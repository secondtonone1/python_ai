## 1. 总体架构

```
+------------------------------- 前端层 ---------------------------------+
|  index.html 来访者聊天页             staff.html 咨询师工作台            |
|  (WebSocket 流式渲染)               (实时推送/接入/回复/AI润色/统计)     |
+-----------|----------------------------------------|-------------------+
            | REST (HTTP)               REST (HTTP)   |
            | + WebSocket 长连接                       |
+-----------v----------------------------------------v-------------------+
|                         FastAPI 应用 (asyncio 内核)                     |
|  api/chat.py 访客接口      api/staff.py 客服接口                         |
|  api/ws.py WebSocket      api/pages.py 页面                             |
|  main.py: 应用工厂 + lifespan 生命周期 + 统一异常映射                     |
+------------------------------------|------------------------------------+
|                       service 业务层                                    |
|  chat_service 编排: 限流->会话->引擎->流式输出->转人工                     |
|  staff_service 人工 / bot_engine 可插拔AI引擎 / rate_limiter / ws_manager|
+------------------------------------|------------------------------------+
|                   dao 数据访问层 (DBUtils 连接池)                         |
|      session_dao / message_dao / knowledge_dao / staff_dao              |
+------------------------------------|------------------------------------+
|    common: 常量/异常/配置/日志     |   schema: Pydantic 请求响应模型      |
+------------------------------------|------------------------------------+
|                      MySQL (ai_service_db)                              |
|          t_session / t_message / t_knowledge / t_staff                  |
+-------------------------------------------------------------------------+
```

**分层原则**：上层依赖下层，下层不感知上层。业务层不碰 HTTP/WebSocket，
数据层只写 SQL —— 后续替换 AI 引擎、升级存储，改动都局限在单层内。

## 2. 技术选型

| 技术 | 选择 | 理由 |
|---|---|---|
| Web 框架 | FastAPI | AI 生态事实标准(langchain/dify 生态均基于它)；原生 asyncio；自动生成接口文档 |
| ASGI 服务器 | uvicorn | FastAPI 官方推荐 |
| 实时通道 | WebSocket | 浏览器原生长连接，支撑流式输出与实时推送 |
| 数据库驱动 | pymysql | 课程 90 已学习 |
| 连接池 | DBUtils(PooledDB) | 业界纯 Python 标准方案 |
| 参数校验 | Pydantic v2 | FastAPI 内置，声明式校验 |
| 配置 | JSON 文件 + 单例 | 零依赖，点号路径读取 |
| 日志 | logging + RotatingFileHandler | 标准库，统一格式 + 文件轮转 |
| 测试 | unittest + TestClient | 标准库 + FastAPI 自带测试客户端 |

## 3. 模块设计

### 3.1 common 基础层

| 模块 | 职责 |
|---|---|
| constants.py | 会话状态/消息角色/WS 消息类型/错误码/满意度取值 |
| exceptions.py | MonitorError 基类 + Param/Auth/NoPermission/NotFound/RateLimit 子类 |
| config.py | Config 单例，点号路径读取 config.json |
| logger.py | 统一日志格式，控制台+文件双输出，按大小轮转 |

### 3.2 schema 层（FastAPI 教学核心）

所有接口入参/出参用 Pydantic 模型声明：
自动参数校验（非法输入返回 400 统一格式）、自动生成 /docs 文档、
响应模型自动过滤字段。见 `schema/models.py`。

### 3.3 dao 数据层

| 模块 | 职责 | 关键点 |
|---|---|---|
| db_pool.py | DBUtils 连接池单例 | cursor() 上下文管理器自动提交/回滚/归还 |
| session_dao.py | 会话增查/状态流转/超时归档/状态统计 | 状态机 SQL 落点 |
| message_dao.py | 消息增查/评价/机器人统计 | idx(session_id, id) 支撑历史与增量拉取 |
| knowledge_dao.py | 知识库 CRUD/命中计数 | 动态 SET 子句的字段白名单更新 |
| staff_dao.py | 客服账号查询 | 密码哈希校验在 service 层 |

**惰性池设计**：DAO 通过 `@property` 惰性获取连接池单例 ——
模块导入阶段不依赖池就绪，真正执行 SQL 时才连接（支撑"数据库瞬时不可用不崩溃"）。

### 3.4 service 业务层

| 模块 | 职责 | 关键点 |
|---|---|---|
| bot_engine.py | **BotEngine 抽象基类 + RuleEngine 规则实现** | 项目 AI 核心，可插拔设计 |
| chat_service.py | 访客侧编排：限流→校验→入库→引擎→流式输出→转人工 | 阻塞部分整体 run_in_executor |
| staff_service.py | 登录/接管/回复/关闭/统计/知识库管理 | 回复拆分为同步入库 + 异步推送 |
| rate_limiter.py | 滑动窗口限流器 | 时间注入可测，锁保证线程安全 |
| ws_manager.py | 访客 WebSocket 连接注册表 | 按会话广播 (流式分片/客服回复推送) |
| staff_ws_manager.py | 工作台 WebSocket 连接注册表 | **全客服广播**: 会话/消息事件实时推送, 替代 3s/5s 轮询 |

### 3.5 api 接口层

| 模块 | 职责 |
|---|---|
| chat.py | 访客 REST：创建会话/历史/评价（同步 def，自动进线程池） |
| ws.py | WebSocket 流式对话 + 心跳 |
| staff.py | 客服 REST 全套（依赖注入鉴权） |
| pages.py | 前端页面路由 |
| main.py | create_app 工厂 + lifespan + 三级异常映射 |

## 4. AI 引擎设计（项目灵魂）

```python
BotEngine (抽象基类, reply 方法)
    ├── RuleEngine    本阶段: 关键词匹配 + 追问状态机 + 转人工
    └── LLMEngine     后续阶段: LangChain 封装真实大模型 (规划)
```

**引擎与业务解耦**：
1. 引擎不碰数据库 —— 知识列表由 service 查询后传入，引擎是纯函数（易于单元测试）；
2. 引擎输出统一 `BotReply` 数据类（答案/来源/命中条目/追问选项/是否转人工）；
3. 后续接入真实 LLM：实现 `LLMEngine(BotEngine)` 一个类即可，业务代码零改动。

**规则引擎匹配算法**：
```
得分 = Σ(命中的关键词, 每个 +1) + (标准问题全文出现 ? +2 : 0)
唯一最高分 -> 直接回答; 多条并列最高分 -> 追问澄清; 无命中 -> 转人工
追问状态(内存): 访客回复序号 -> 从候选列表取出对应答案
```

**流式输出**：真实 LLM 逐 token 返回；本项目按标点分句、长句按 8 字切块，
WebSocket 每 50ms 推一个分片 —— 模拟打字机效果，接入真实模型时替换分片来源即可。

## 5. 并发模型（教学重点）

| 场景 | 机制 | 对应课程 |
|---|---|---|
| 同步 def 端点(纯 DB 操作) | FastAPI 自动放进 uvicorn 线程池 | 67-70 线程池 |
| async def 端点(WebSocket) | 事件循环直接执行 | 73-83 协程 |
| 聊天处理中的阻塞 DB/引擎计算 | `loop.run_in_executor` 交给线程池 | 88 课"协程+线程池"模式 |
| 客服回复 = 入库 + 推送 | 拆成"同步入库(线程池) + 异步推送(事件循环)"两步 | 82 生产者消费者思想 |
| 工作台实时推送(替代轮询) | 消息入库/状态变更点经 StaffWsManager 向全部工作台 WebSocket 广播 | 82 发布订阅 / 84-89 长连接 |
| 后台会话归档 | asyncio 周期任务 | 75 事件循环调度 |

**设计原则**：事件循环里绝不跑阻塞代码；阻塞代码统一进线程池；
一个请求内同步与异步职责明确拆分。

## 7. 会话状态机

```
                访客发消息
   +---------------------------------------+
   |              bot (机器人接待)           |
   +-----+--------------------+-------------+
  未命中转人工                | 命中/追问
   |                         v
   |              (继续机器人接待, 循环)

+----------------+                  +----------+                  +--------+
        |                              |
        +--- 30 分钟无活动 ------------+----> archived (超时归档, 后台任务)
```

## 8. 异常与错误码体系

| 错误码 | 含义 | 场景 |
|---|---|---|
| 200 | 成功 | 所有正常响应 |
| 400 | 参数错误 | Pydantic 校验失败、业务参数校验 |
| 401 | 未认证/认证失败 | 缺少 X-Staff-Id、登录失败 |
| 403 | 无权限 | 未接管会话就回复等 |
| 404 | 资源不存在 | 会话/消息/知识条目不存在 |
| 429 | 限流 | 消息/建会话超频（带 Retry-After 响应头） |
| 500 | 服务器内部错误 | 未预期异常（堆栈进日志，对外隐藏细节） |

三级异常映射（main.py）：
1. MonitorError → 对应错误码 JSON
2. RequestValidationError → 400 统一格式
3. Exception 兜底 → 500 统一格式（日志记录完整堆栈）

## 9. 可靠性设计

| 场景 | 设计 |
|---|---|
| 数据库瞬时不可用 | 启动不退出（仅告警），连接池懒建连，恢复后自动可用 |
| 接口防刷 | 滑动窗口限流：聊天 20 条/分钟/会话，建会话 10 次/分钟/IP |
| 前端 XSS | 所有动态内容用 textContent 渲染，不用 innerHTML |
| 日志膨胀 | RotatingFileHandler 10MB 轮转保留 5 份 |
| 会话堆积 | 后台任务每 60s 归档超时(30min)会话 |
| 访客掉线 | 前端 WebSocket 断线自动重连（3s 间隔） |
| 限流器内存膨胀 | 后台清理超过 2 个窗口无访问的 key |
